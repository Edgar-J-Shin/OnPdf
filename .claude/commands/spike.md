# Role: Research Engineer

$ARGUMENTS 에 대한 기술 검증(spike)을 수행한다. 목적은 **제품 코드가 아니라 결정**이다.

계획서(`pdf-editor-plan.md`) 8장 위험 항목처럼 결과를 모르는 문제에 쓴다. 예: 한글 CID 폰트 임베딩 왕복, PDFium 특정 API 동작, 타일 렌더링 성능, HarfBuzz 서브셋, 증분 저장과 서명 보존.

## 프로세스

1. **이슈·브랜치 준비 (git flow)**
   - `git branch --show-current` 가 `develop`/`main` 이거나 이슈 번호가 없는 브랜치면: `gh issue list` 로 해당 작업 이슈를 찾고, 없으면 `gh issue create` 로 만든다 (제목 접두 `M0:`~`M5:`, `--milestone`, 필요 시 라벨). 그 다음 `git checkout develop && git pull && git checkout -b spike/{이슈번호}-{slug}` 로 분기한다
   - 이미 이슈 번호 브랜치에 있으면 그대로 진행
   - 확정된 브랜치명을 `{branch}` 로 쓴다
2. 검증할 질문을 **한 문장**으로 고정하고, 성공/실패 판정 기준을 먼저 적는다
3. 조사:
   - PDFium 고정 버전 헤더(`third_party/`)와 PDFium 저장소의 테스트 코드(`testing/embedder_test`)에서 해당 API 사용 예 확인
   - qpdf / HarfBuzz / Qt 문서 확인 (필요 시 WebSearch)
4. 실험 코드 작성: `cli/` 의 서브커맨드 또는 `tests/spike/` 아래 **격리된** 코드. 제품 레이어(core/edit/app) 수정 최소화
5. 실행·측정: 입력 PDF(한글·스캔본·폼·암호화 포함), 결과 파일, 타 뷰어 표시 확인, 수치(시간·메모리·파일 크기)
6. 결론과 권고 작성

## 산출물 구조 (`01-spike.md`)

```markdown
# [주제] 기술 검증

## 질문
- 한 문장 + 판정 기준

## 조사 결과
- 사용 API / 문서 / 참고 코드 링크
- 제약·버그·버전 이슈

## 실험
- 코드 위치, 입력 파일, 실행 방법
- 결과 (표: 입력 → 결과 → 수치)

## 결론
- 판정: 가능 / 조건부 가능 / 불가
- 권고: 채택할 설계, 계획서 수정 필요 여부(범위·일정)
- 후속: 제품 코드로 옮길 때 할 일, 추가 테스트
```

## 준수사항
- 기간 상한 2주. 넘길 것 같으면 중간 결과로 보고
- 실험 코드는 머지하지 않거나 `tests/spike/` 에만 남긴다. 제품 코드에 섞지 않는다
- 테스트 PDF 는 라이선스 확인된 것만 `testdata/` 에 추가
- 결론이 계획서와 충돌하면 계획서 수정안을 함께 제시

## 완료 후 승인 절차 (필수 실행)

### Step 1: 완료 보고
산출물 경로, 판정, 권고를 텍스트로 출력한다.

### Step 2: 다음 단계 확인 (AskUserQuestion 필수 사용)
**반드시 `AskUserQuestion` 도구를 호출**하여 사용자에게 묻는다:

- question: "검증 결과를 반영할 다음 단계를 선택해주세요."
- options: ["기능 기획 진행 (/planning)", "계획서 수정", "여기서 중단"]

### Step 3: 응답에 따른 분기
- **"기능 기획 진행"** → `Skill` 도구로 `/planning` 명령을 **즉시** 실행한다
- **"계획서 수정"** → `pdf-editor-plan.md` 의 해당 절 수정안을 제시하고 승인 후 반영
- **"여기서 중단"** → 워크플로우 중단 안내
